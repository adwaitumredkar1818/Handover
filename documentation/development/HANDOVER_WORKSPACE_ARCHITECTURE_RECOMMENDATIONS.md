## 1. Architectural Alignment with Platform Directives

The Handover platform's permanent governance (defined in `AGENTS.md`) establishes six core rules that directly dictate the architecture of the Handover Workspace:
1. **PostgreSQL Is Canonical**: PostgreSQL must remain the single source of truth for all handover cases, package versions, sections, links, signoffs, and audit logs.
2. **Project Membership != Source Access**: Even when a handover package is approved, downstream recipients must not gain unauthorized access to underlying restricted source artifacts unless explicitly permitted by source ACLs.
3. **LLM Is Not Source of Truth**: Handover narratives and summaries generated by AI (`qwen3:8b`) must strictly cite supporting evidence and must never approve handovers, decide task completion, or override permissions independently.
4. **Human Approval Governance**: Handover packages require explicit human signoff by designated project roles; recipient receipt acknowledgement can never substitute for reviewer approval.
5. **Epistemic Separation**: The UI and data contracts must clearly delineate original evidence, AI-extracted knowledge, and human-verified findings.
6. **Zero Fabrication**: No synthetic findings, dummy users, or mock project identifiers may be represented as real project handover assets.

## 4. Epistemic Separation & Verification Center Integration

### Architecture Pattern: Strict Upstream Gating
```
[ Reconstructed Knowledge ] ──▶ [ Verification Center ] ──▶ [ Handover Assembly Engine ]
  (Status: candidate)            (Status: human_verified)     (epistemic_status check)
                                                                       │
                                                                       ▼
                                                          [ HandoverPackageSection ]
                                                          (Immutable version snapshot)
```

### Engineering Rules:
1. **No Provisional Findings Without Explicit Labeling**:
   - `PackageAssemblyService` must only include `KnowledgeItem` records where `review_status = 'approved'` and `epistemic_status = 'human_verified'`.
   - If an unverified finding is explicitly added by a project manager, it must carry an epistemic badge:
     `<Badge variant="outline" className="border-amber-500 text-amber-500">Provisional / Unverified</Badge>`.
2. **Evidence Attribution**:
   - Every assembled knowledge item must render its underlying citation link to the original `EvidenceItem` or `EvidenceChunk`.
   - Clicking a citation must open the contextual evidence viewer or navigate to the Evidence Workspace.

## 5. Conflict Management Integration & Handover Gating

### Architecture Pattern: Blocking Readiness Assessment
The Handover Workspace must never exist in a silo from the Conflict Management module. An unresolved contradiction in technical architecture or system ownership directly invalidates handover completeness.

### Engineering Rules:
1. **Readiness Engine Gate**:
   - In `backend/app/services/handover_readiness.py`, the `conflict_resolution` category queries `VerificationConflict` where `project_id = case.project_id` and `resolution_status = 'unresolved'`.
   - If unresolved conflicts exist, the category score is set to `0%` and a critical blocker is returned:
     `{"category": "conflict_resolution", "severity": "BLOCKER", "message": "22 unresolved contradictions detect in project knowledge."}`.
2. **Frontend Alert Banner**:
   - In `HandoverDetailPage.tsx`, whenever `readiness.conflict_resolution < 100%`, a prominent callout banner must render at the top:
     ```tsx
     <Alert variant="destructive">
       <AlertTriangle className="h-4 w-4" />
       <AlertTitle>Critical Handover Blocker</AlertTitle>
       <AlertDescription>
         There are unresolved contradictions in this project's verified knowledge.
         Handovers cannot be submitted for supervisor approval until all conflicts are investigated.
         <Link href="/conflicts" className="underline ml-2">Open Conflict Management Workspace →</Link>
       </AlertDescription>
     </Alert>
     ```
3. **Approval Action Disabling**:
   - Disable the "Submit for Signoff" button while any blocking readiness issues remain active.

## 6. Concurrency Control & State Machine Integrity

### Optimistic Concurrency Control (OCC)
In multi-party handover reviews, concurrent edits by the outgoing author, peer reviewer, and supervisor can overwrite state.
- **Backend**: `HandoverCase.lock_version` integer column is incremented on every update. If `payload.lock_version != current.lock_version`, backend raises HTTP 409 Conflict.
- **Frontend Recommendation**:
  - Store `lock_version` in local case state upon fetch.
  - Include `lock_version` in all `PUT /cases/{id}` and `POST /cases/{id}/status` requests.
  - If HTTP 409 is received, prompt user:
    *"This handover was updated by another team member. Click to refresh the latest state."*

### Separation of Duties Enforcement
To maintain audit integrity:
- Outgoing author **cannot** approve their own handover as `supervisor` or `peer_reviewer`.
- Incoming recipient **cannot** sign off on supervisor approval.
- **Frontend Action**: Dynamically inspect the current user's identity (`useAuth().user.id`) against `case.outgoing_user_id` and disable unauthorized signoff role options in the signoff dialog.

## 7. Export Engine Architecture

### Multi-Format Distribution
The Handover Workspace must support 3 distinct distribution tiers:
1. **Markdown (`GET /cases/{id}/export/markdown`)**:
   - Designed for developer consumption, git repository documentation, and README generation.
   - Must include frontmatter, table of contents, all 8 sections, and markdown citations.
2. **JSON (`GET /cases/{id}/export/json`)**:
   - Machine-readable package conforming to the platform interchange schema.
   - Includes raw structured items, cryptographic hashes, and participant metadata for external auditing.
3. **PDF (`GET /cases/{id}/export/pdf`)**:
   - Executive and compliance document generated via PyMuPDF.
   - Clean, professional layout with page numbers, cover page, executive summary, and approval signatures.
